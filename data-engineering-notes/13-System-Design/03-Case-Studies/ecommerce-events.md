

# E-Commerce Events — Data System Design Case Study

## 1. Problem Statement

Design a scalable data platform that collects, processes, and analyzes e-commerce events across the customer journey, from product discovery to order delivery and returns.

An e-commerce event represents an action or business occurrence, such as a product view, cart update, order placement, payment confirmation, shipment, or refund.

The platform must support both near-real-time analytics and historical reporting while maintaining data quality, reliable event processing, and correct business metrics.

### Example Customer Journey

```text
Visit Website
     |
     v
Search Product
     |
     v
View Product
     |
     v
Add to Cart
     |
     v
Place Order
     |
     v
Payment Confirmed
     |
     v
Order Shipped
     |
     v
Order Delivered
```

Each step can produce one or more events. Some events originate from the customer application, while others come from backend systems.

**Important:** A customer action and a confirmed business transaction are not always the same thing. For example, clicking the Place Order button does not prove that an order was successfully created or paid for.

## 2. Business Requirements

The platform should help the business answer questions such as:

- How many orders are placed each hour?
- What is the payment success rate?
- Which products generate the most sales?
- How many customers abandon their carts?
- What is the average order value?
- How much revenue is generated by each campaign?
- How many orders are delayed or canceled?
- What is the refund rate?
- Which products have high return rates?
- How does customer behavior change over time?

### Functional Requirements

1. Collect events from web applications, mobile applications, and backend services.
2. Ingest events continuously or incrementally.
3. Preserve raw event data.
4. Validate schemas and required fields.
5. Identify duplicate events and handle out-of-order delivery.
6. Process orders, payments, shipments, cancellations, and refunds.
7. Build customer, product, order, and event-level datasets.
8. Calculate business metrics and funnel conversion.
9. Support real-time monitoring and historical reporting.
10. Support reprocessing and historical corrections.

### Non-Functional Requirements

| Requirement | Design consideration |
|---|---|
| Scalability | Handle traffic spikes during promotions |
| Reliability | Recover from failures without corrupting results |
| Data freshness | Publish metrics within agreed latency targets |
| Correctness | Prevent duplicate orders and incorrect revenue |
| Availability | Keep critical ingestion and analytics services operational |
| Security | Protect customer and payment-related information |
| Observability | Track failures, lag, freshness, and data quality |
| Cost efficiency | Control compute, storage, and serving costs |

The actual throughput, retention, latency, and availability targets should be agreed upon before sizing the architecture.

## 5. Event Schema Design

A consistent event schema makes processing, validation, deduplication, and analysis easier.

### Example Event

```json
{
  "event_id": "evt-10001",
  "event_type": "order_created",
  "event_time": "2026-10-31T10:30:00Z",
  "event_version": 1,
  "source_system": "order-service",
  "customer_id": "cust-501",
  "order_id": "ord-9001",
  "currency": "INR",
  "order_total": 2499.00,
  "ingestion_time": "2026-10-31T10:30:02Z"
}
```

### Important Fields

| Field | Purpose |
|---|---|
| `event_id` | Identifies an individual logical event |
| `event_type` | Describes the business occurrence |
| `event_time` | Time when the event occurred |
| `event_version` | Supports schema evolution |
| `source_system` | Identifies the originating service |
| `customer_id` | Identifies the customer, when available |
| `order_id` | Identifies the related order |
| `currency` | Defines the monetary currency |
| `order_total` | Represents the documented order amount |
| `ingestion_time` | Records when the platform received the event |

Not every event requires every field. For example, a product-view event may not contain an `order_id`.

### Schema Design Rules

1. Define required and optional fields for each event type.
2. Use consistent naming conventions.
3. Include an event identifier and source metadata.
4. Store timestamps with clearly defined time-zone semantics.
5. Version schemas when changing event structure.
6. Define monetary amounts and currency explicitly.
7. Preserve enough metadata for debugging and reprocessing.
8. Avoid collecting unnecessary personal or sensitive information.

**Important:** `event_id` identifies an event, whereas `order_id` identifies a business order. One order can legitimately generate many different events.

## 6. Event Delivery and Message Broker Design

A message broker such as Apache Kafka or Azure Event Hubs separates event producers from downstream consumers.

### Why Use a Broker?

- Buffer traffic spikes.
- Decouple applications from analytics systems.
- Support multiple consumers.
- Allow replay within configured retention.
- Enable parallel processing.
- Reduce the need for producers to know downstream implementation details.

### Partitioning

Events can be partitioned by a key such as `order_id` or `customer_id`.

**Partitioning by `order_id`:**
- Can help preserve ordering for events belonging to the same order.
- Is useful when order lifecycle processing is important.
- Can still produce skew if certain orders generate unusually large event volumes.

**Partitioning by `customer_id`:**
- Can help group customer activity.
- May be useful for customer-level processing.
- Does not automatically guarantee global ordering across the topic.

Kafka ordering is guaranteed within a partition, not across all partitions.

### Consumer Groups

Separate consumer groups can independently process the same event stream.

For example:

```text
                    Orders Topic
                         |
            +------------+------------+
            |            |            |
            v            v            v
       Analytics      Monitoring    Search Index
       Consumer       Consumer      Consumer
```

Each group can maintain its own progress and processing behavior.

## 7. Raw, Silver, and Gold Data Layers

A medallion architecture separates raw ingestion from cleaned and business-ready data.

### Bronze: Raw Events

Preserve the original event payload and ingestion metadata.

Typical fields include:

- Original payload.
- Source system.
- Event ID.
- Ingestion timestamp.
- Broker topic, partition, and offset where available.
- Schema version.
- Pipeline run or batch ID.

Raw storage helps investigate incorrect results and rebuild downstream tables after transformation logic changes.

### Silver: Cleaned Events

Silver data contains validated and standardized events.

Typical operations:

- Parse and validate event schemas.
- Standardize timestamps and currency representation.
- Identify duplicate event IDs.
- Handle malformed records.
- Normalize event types.
- Apply privacy rules.
- Enrich events with reference data.
- Preserve rejected records in quarantine.

### Gold: Business-Ready Data

Gold tables contain metrics and datasets designed for business analysis.

Examples:

- Daily order summary.
- Payment success and failure metrics.
- Product sales summary.
- Cart conversion funnel.
- Customer order history.
- Refund and cancellation metrics.
- Delivery performance.

These layers describe logical responsibilities; the implementation may use different physical tables or storage layouts.

## 8. Deduplication and Idempotency

Duplicate events can appear because of producer retries, broker replay, processing retries, or partial failures.

### Example

| event_id | event_type | order_id |
|---|---|---|
| evt-101 | order_created | ord-100 |
| evt-102 | payment_captured | ord-100 |
| evt-102 | payment_captured | ord-100 |

The last two rows represent the same logical event if `event_id` is a reliable unique identifier.

### Deduplication Strategy

1. Use a stable event ID.
2. Validate the source's uniqueness guarantees.
3. Deduplicate within a defined scope.
4. Use a deterministic tie-breaker if several copies exist.
5. Make target writes safe to retry.
6. Monitor duplicate rates.

A simplified batch deduplication example:

```python
from pyspark.sql import functions as F
from pyspark.sql.window import Window

window_spec = (
    Window
    .partitionBy("event_id")
    .orderBy(
        F.col("ingestion_time").desc(),
        F.col("source_sequence").desc()
    )
)

deduplicated_df = (
    events_df
    .withColumn(
        "row_num",
        F.row_number().over(window_spec)
    )
    .filter(F.col("row_num") == 1)
    .drop("row_num")
)
```

This example assumes that the ordering fields exist and correctly identify the preferred copy. Add another stable tie-breaker if they can tie.

### Idempotency

Idempotency means that repeating the same logical operation produces the same final effect under defined conditions.

For an order pipeline, repeatedly processing the same `order_created` event should not create multiple analytical order records.

Common techniques include:

- Upsert or MERGE by business key.
- Stable event identifiers.
- Deduplication before writing.
- Controlled partition replacement for historical rebuilds.
- Recording source progress only after successful target commits.

A MERGE operation alone is not a complete guarantee of correctness. The source must be deduplicated appropriately, matching conditions must be correct, and concurrent writes must be handled safely.

## 9. Order Lifecycle and Event Ordering

An order can move through multiple states.

```text
Created
   |
   v
Payment Pending
   |
   v
Paid
   |
   v
Processing
   |
   v
Shipped
   |
   v
Delivered
```

However, real systems also support cancellation, payment failure, partial fulfillment, returns, and refunds.

Events can arrive out of order because of retries, independent services, or network delays.

### Example

```text
Event A: order_created
Event B: payment_captured
Event C: order_cancelled
```

If these events arrive in a different order, the processing system must not blindly apply them in arrival order without considering their meaning.

### Recommended Design

- Include a source sequence number or version when available.
- Preserve event timestamps and ingestion timestamps separately.
- Use authoritative source state for reconciliation.
- Define valid state transitions.
- Handle duplicate and stale events.
- Separate payment state from order state.
- Support correction events where business processes allow them.

A timestamp alone may not be enough to determine correct order when clocks differ or events share the same timestamp. Source sequence numbers, versions, or authoritative state are often more reliable.

## 10. Data Modeling

Data modeling should begin with the grain of each dataset.

### 10.1 Event Fact Table

**Grain:** One row per accepted logical business event.

Example: `fact_ecommerce_event`

| Column | Description |
|---|---|
| `event_id` | Unique event identifier |
| `event_type` | Event type |
| `event_timestamp` | Business event time |
| `customer_key` | Customer dimension key |
| `order_key` | Order dimension key, when applicable |
| `product_key` | Product dimension key, when applicable |
| `source_system` | Event origin |
| `event_count` | Usually 1 per event row |

### 10.2 Order Fact Table

**Grain:** One row per order, if designed as an order-level fact.

Example: `fact_order`

| Column | Description |
|---|---|
| `order_key` | Warehouse surrogate key |
| `order_id` | Business order identifier |
| `customer_key` | Customer dimension key |
| `order_date_key` | Order date |
| `order_status` | Current or modeled status |
| `gross_order_amount` | Defined gross amount |
| `discount_amount` | Defined discount amount |
| `net_order_amount` | Defined net amount |

The monetary columns need explicit business definitions. For example, whether shipping, tax, discounts, and refunds are included depends on the agreed metric.

### 10.3 Payment Fact Table

**Grain:** One row per payment transaction or payment attempt, depending on the design.

A single order may have several payment attempts, partial captures, or refunds.

Do not assume one order always corresponds to one payment record.

### 10.4 Dimensions

Possible dimensions include:

- `dim_customer`
- `dim_product`
- `dim_date`
- `dim_campaign`
- `dim_channel`
- `dim_payment_method`

Avoid joining facts with different grains directly without considering duplication. Aggregate to compatible grains before comparing measures.

## 11. Business Metrics and SQL

Metric definitions should be agreed upon before implementation. The examples below are illustrative.

### 11.1 Orders Created by Day

```sql
SELECT
    CAST(event_time AS DATE) AS order_date,
    COUNT(DISTINCT order_id) AS orders_created
FROM silver.ecommerce_events
WHERE event_type = 'order_created'
GROUP BY CAST(event_time AS DATE)
ORDER BY order_date;
```

This assumes `order_created` is emitted once per logical order or that `order_id` is a reliable identifier.

### 11.2 Payment Success Rate

A common definition is:

\[
\text{Payment Success Rate} =
\frac{\text{Successful Payment Attempts}}
{\text{Eligible Payment Attempts}}
\times 100
\]

The query should use payment-attempt identifiers and an agreed definition of eligible attempts.

Counting all `payment_captured` events and dividing by all order-created events may produce a misleading result because the numerator and denominator represent different entities.

### 11.3 Average Order Value

A common definition is:

\[
\text{AOV} =
\frac{\text{Defined Order Revenue}}
{\text{Number of Qualifying Orders}}
\]

The revenue definition should specify treatment of discounts, taxes, shipping, cancellations, and refunds.

### 11.4 Product Sales

A sales report should use an order-item or sales fact table if the business needs product-level quantities and amounts.

A simple order event may not contain enough detail to calculate product revenue accurately, especially when orders contain multiple products.

## 12. Revenue, Refunds, and Financial Correctness

Financial analytics require special care because order and payment events represent different business facts.

Consider the following:

```text
Order Created:       ₹2,000
Payment Captured:    ₹2,000
Partial Refund:        ₹500
```

The captured payment is ₹2,000, but net cash captured after the refund is ₹1,500, ignoring fees and other adjustments.

That does not automatically mean recognized accounting revenue is ₹1,500. Accounting revenue depends on the business's accounting policies and applicable rules.

### Recommended Practices

- Track orders, payment attempts, captures, refunds, and chargebacks separately.
- Use stable identifiers for each business transaction.
- Avoid summing repeated order-total snapshots as new revenue.
- Define gross, net, and refunded amounts precisely.
- Preserve corrections and reversals.
- Reconcile analytics with authoritative order and payment systems.
- Use currency-aware calculations.

**Interview point:** Do not calculate revenue by blindly summing every monetary field from every event type.

## 14. Late Events and Reprocessing

Events may arrive late because of service outages, retries, broker backlog, or network interruptions.

### Handling Late Events

1. Preserve the original event timestamp.
2. Record ingestion time separately.
3. Use event-time processing for time-based metrics.
4. Configure watermarks for supported stateful operations.
5. Retain raw events for historical correction.
6. Reprocess affected time ranges when necessary.

Watermarks do not guarantee that every late event will be included. Some events may arrive after the state required for their calculation has been discarded.

### Reprocessing Example

Suppose a bug caused order events from October 20 to be incorrectly classified.

A safe recovery process is:

1. Identify the affected date range and business entities.
2. Read the retained raw events.
3. Correct the transformation logic.
4. Rebuild the affected Silver or Gold datasets.
5. Use a controlled overwrite or idempotent merge.
6. Reconcile counts and monetary totals.
7. Publish the corrected results.

Do not rerun a pipeline blindly if the target may already contain partially committed data.

## 15. Data Quality and Reconciliation

Important checks include:

- Required event IDs and event types are present.
- Order IDs exist for order-related events.
- Monetary values follow the expected schema.
- Event timestamps are valid.
- Duplicate event IDs are detected.
- Order state transitions are valid.
- Refunds reference appropriate transactions.
- Target counts reconcile with source expectations.
- Business aggregates are consistent with authoritative systems.

### Example: Detect Duplicate Event IDs

```sql
SELECT
    event_id,
    COUNT(*) AS row_count
FROM silver.ecommerce_events
GROUP BY event_id
HAVING COUNT(*) > 1;
```

### Example: Detect Missing Order IDs

```sql
SELECT COUNT(*) AS invalid_event_count
FROM silver.ecommerce_events
WHERE event_type IN (
    'order_created',
    'order_cancelled',
    'payment_captured',
    'refund_completed'
)
AND order_id IS NULL;
```

These checks assume the selected event types require an order ID. Event contracts should define those requirements explicitly.

Record invalid events in quarantine with the source payload, failure reason, event ID where available, and processing metadata.

## 16. Security and Privacy

E-commerce events can contain customer identifiers, behavioral information, and sensitive transaction metadata.

### Recommended Controls

- Use authentication for producers and consumers.
- Apply least-privilege access to topics and datasets.
- Encrypt data in transit and at rest.
- Avoid storing card numbers, passwords, or payment secrets in event payloads.
- Limit personal data collection to necessary fields.
- Mask or pseudonymize identifiers where appropriate.
- Apply retention and deletion policies.
- Audit access to sensitive data.
- Restrict raw-event access when it contains more sensitive details than curated datasets.

Pseudonymized identifiers may still be personal data. Access controls and privacy obligations can continue to apply.

## 17. Scaling and Performance

E-commerce traffic can increase sharply during sales campaigns, holidays, or product launches.

### Scaling Strategies

**Partitioned ingestion:** Distribute events across broker partitions using an appropriate key.

**Horizontal processing:** Add compute capacity when the workload can use it.

**Incremental processing:** Process newly arrived or affected records rather than rescanning all historical data.

**Columnar storage:** Use formats such as Parquet for analytical workloads.

**Partition pruning:** Organize and query data so that only relevant partitions need to be scanned.

**Pre-aggregation:** Store common business summaries when doing so improves query performance.

**Small-file management:** Avoid producing excessive small files in the lakehouse.

### Monitor

- Events per second.
- Processing throughput.
- Consumer lag.
- End-to-end freshness.
- Invalid and duplicate event rates.
- Streaming failures.
- Storage growth.
- Query duration.
- Cost per processed volume.

Adding workers does not always solve performance problems. A hot partition, slow destination, skewed key, or serial operation may remain the bottleneck.

## 19. Capacity Estimation

Assume an e-commerce business generates:

- 20 million events per day.
- Average raw event size of 1 KB before compression.

### Average Events per Second

\[
\text{Average EPS} =
\frac{20{,}000{,}000}{86{,}400}
\approx 231
\]

The average is approximately 231 events per second.

Peak traffic can be substantially higher, particularly during promotions.

### Raw Storage per Day

\[
20{,}000{,}000 \times 1\text{ KB}
\approx 20\text{ GB/day}
\]

### Raw Storage per Year

\[
20\text{ GB/day} \times 365
\approx 7.3\text{ TB/year}
\]

This is a rough estimate before compression, replication, metadata, and derived tables.

Actual capacity planning must also consider:

- Peak events per second.
- Event-size distribution.
- Broker retention.
- Replication.
- Compression.
- Bronze, Silver, and Gold storage.
- Backfills and replay.
- Number of downstream consumers.
- Query workloads.
- Growth and operational headroom.

## 20. Failure Scenarios and Recovery

| Failure | Recommended response |
|---|---|
| Producer retries | Use stable event IDs and safe deduplication |
| Broker backlog | Investigate processing throughput and partition skew |
| Streaming job failure | Recover using compatible checkpoints and safe sink semantics |
| Invalid event schema | Quarantine invalid data and investigate schema changes |
| Duplicate payment event | Deduplicate using transaction/event identity |
| Out-of-order order events | Apply source sequence/version and valid state-transition rules |
| Incorrect transformation | Reprocess affected data from retained raw events |
| Target write partially completed | Inspect committed output and rerun idempotently |
| Missing historical events | Reconcile with authoritative sources and backfill |
| Payment/revenue mismatch | Reconcile order, capture, refund, and chargeback records |

A pipeline run marked `FAILED` may still have committed output. Always inspect the target state before restarting or reprocessing.

## 22. Common Interview Mistakes

1. Treating every event as a unique order.
2. Treating payment authorization as payment capture.
3. Counting repeated order-total snapshots as separate revenue.
4. Ignoring refunds, cancellations, and chargebacks.
5. Assuming all events arrive in order.
6. Deduplicating orders using `event_id` alone without understanding business grain.
7. Joining event-level and order-level facts without considering row multiplication.
8. Defining conversion metrics without a clear denominator.
9. Assuming checkpointing alone prevents duplicates.
10. Ignoring late events and historical corrections.
11. Storing unnecessary sensitive customer information.
12. Estimating capacity from average traffic alone.
13. Monitoring pipeline status without reconciling business results.

## 23. Interview Questions and Answers

### Q1. How would you design an e-commerce event platform?

I would define the event contracts, ingest events through Kafka or Event Hubs, preserve raw data, process and validate events with Spark, build curated analytical tables, and serve metrics through a SQL warehouse or BI platform. I would also include idempotency, monitoring, privacy, and reprocessing.

### Q2. Why distinguish event IDs from order IDs?

An event ID identifies one logical event. An order ID identifies a business order. One order can generate many legitimate events, so the two identifiers serve different purposes.

### Q3. How do you prevent duplicate orders?

Use the business order key, reliable source-of-truth rules, idempotent upserts, and source deduplication where appropriate. Also reconcile the analytical order table with the authoritative order system.

### Q4. How do you handle out-of-order events?

Preserve event time and ingestion time, use source sequence numbers or versions where available, and define valid state transitions. For critical business states, reconcile with the authoritative source.

### Q5. How do you calculate accurate revenue?

Define the revenue metric first, then use appropriate order, payment, refund, and adjustment facts. Avoid summing repeated snapshots or mixing payment authorization, capture, and refund events.

### Q6. Why maintain separate order and payment facts?

One order may have multiple payment attempts, captures, or refunds. Separate facts preserve the correct grain and avoid multiplying order-level measures.

### Q7. How do you support real-time and historical analytics?

Use a streaming path for fresh metrics and durable raw storage for historical processing. Build curated datasets and aggregates that can serve both operational dashboards and analytical queries.

### Q8. How would you recover from a transformation bug?

Identify the affected period, correct the code, reprocess retained raw data, replace or update the affected target data safely, and reconcile the corrected results.

### Q9. How would you handle payment failures?

Capture payment-attempt events with stable identifiers and clear statuses. Calculate failure rates using eligible payment attempts, not simply the total number of order events.

### Q10. What metrics would you monitor?

Event throughput, consumer lag, freshness, failures, duplicate rate, invalid-event rate, order counts, payment success rate, refund totals, and reconciliation differences.

### Q11. How would you scale for a major sale?

Estimate peak traffic, ensure sufficient broker partitions and processing capacity, test sink throughput, monitor skew and lag, and prepare replay and recovery procedures.

### Q12. What is the most important design principle in e-commerce analytics?

Maintain correct business semantics. The platform must distinguish events, orders, payment transactions, and refunds so that retries and multiple lifecycle events do not produce misleading metrics.

| Gold | Business-ready metrics |
| Idempotency | Safe repeated processing |
| Event ordering | Requires explicit handling |
| Order fact | One row per defined order grain |
| Payment fact | One row per defined payment grain |
| Revenue | Requires agreed business and accounting definitions |
| Reprocessing | Rebuild affected data from retained source events |
| Reconciliation | Compare analytical results with authoritative sources |
| Consumer lag | Indicates delay behind available events |

### Five Key Takeaways

1. Define event contracts and business identifiers before building the pipeline.
2. Distinguish orders, payments, captures, refunds, and cancellations.
3. Make event processing safe to retry and recover.
4. Define the grain and business meaning of every analytical table and metric.
5. Validate business results, not just whether the pipeline ran successfully.
