

# Logs, Metrics, and Traces in Data Engineering

## 1. Introduction

Logs, metrics, and traces are the three main types of telemetry data used in observability.

They help data engineers understand:
- What happened inside a pipeline.
- Whether the pipeline is performing normally.
- Where execution time is being spent.
- Why a job or task failed.
- Which component is causing a problem.

Together, they provide visibility into the health and behavior of data systems.

### Example

Suppose a PySpark pipeline processes 10 million customer records.

During execution, the pipeline becomes unusually slow.

You can investigate using:

- **Logs:** Find error messages, warnings, and execution details.
- **Metrics:** Check execution duration, memory usage, record counts, and CPU utilization.
- **Traces:** Follow the execution path across multiple services and identify where time is being spent.

---

## 2. What Is Observability?

Observability is the ability to understand the internal state of a system by examining the data it produces.

It helps engineers investigate problems without needing to know every possible failure in advance.

For a data pipeline, observability helps answer questions such as:

- Did the pipeline run successfully?
- How many records were processed?
- How long did each stage take?
- Did the source system respond slowly?
- Which transformation caused the failure?
- Is the output data fresh and complete?

### Monitoring vs Observability

| Monitoring | Observability |
|---|---|
| Checks predefined conditions | Helps investigate system behavior |
| Uses dashboards and alerts | Uses logs, metrics, traces, and context |
| Identifies known problems | Helps explore unknown problems |
| Example: Alert when a job fails | Example: Investigate why a job became slow |

Monitoring is an important part of observability.

Observability provides broader information for understanding system behavior.

## 4. Logs

### 4.1 What Are Logs?

Logs are timestamped records of events generated by applications, services, and infrastructure.

They provide detailed information about what happened during execution.

Example:

```text
2026-10-25 06:00:00 INFO Pipeline started
2026-10-25 06:00:05 INFO Reading source data
2026-10-25 06:02:10 INFO Records loaded: 100000
2026-10-25 06:03:15 ERROR Database connection failed
2026-10-25 06:03:16 ERROR Pipeline execution failed
```

From these logs, an engineer can identify:
- When the pipeline started.
- Which operation was running.
- How many records were loaded.
- When the failure occurred.
- What error caused the failure.

### 4.2 Common Log Levels

| Level | Meaning | Example |
|---|---|---|
| DEBUG | Detailed diagnostic information | SQL query parameters |
| INFO | Normal application events | Pipeline started |
| WARNING | Unexpected but non-fatal condition | High processing duration |
| ERROR | Operation failed | Database connection error |
| CRITICAL | Severe failure affecting the system | Critical service unavailable |

The exact log levels and their behavior depend on the logging framework.

### 4.3 Python Logging Example

Python provides a built-in `logging` module.

```python
import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(message)s"
)

logging.info("Pipeline started")
logging.warning("Processing duration is high")
logging.error("Database connection failed")
```

Example output:

```text
2026-10-25 06:00:00 INFO Pipeline started
2026-10-25 06:01:00 WARNING Processing duration is high
2026-10-25 06:02:00 ERROR Database connection failed
```

### 4.4 Logging Exceptions

Use `logger.exception()` inside an exception handler to record the error and traceback.

```python
import logging

logger = logging.getLogger(__name__)

try:
    result = 100 / 0

except Exception:
    logger.exception("Transformation failed")
    raise
```

The `raise` statement ensures the failure is not silently hidden.

### 4.5 Structured Logging

Structured logging stores log information in a consistent format, commonly JSON.

Example:

```json
{
  "timestamp": "2026-10-25T06:00:00Z",
  "level": "ERROR",
  "pipeline": "orders_pipeline",
  "task": "transform_orders",
  "run_id": "run_123",
  "message": "Invalid order amount",
  "environment": "PROD"
}
```

Advantages:
- Easier filtering and searching.
- Consistent log fields.
- Better integration with monitoring platforms.
- Easier correlation between pipeline runs.
- More useful automated alerting.

### 4.6 What Should Be Logged in a Data Pipeline?

Useful information includes:

- Pipeline name.
- Run ID.
- Task or activity name.
- Start and end timestamps.
- Source and target details.
- Input and output record counts.
- Processing duration.
- Error messages.
- Retry attempts.
- Data quality failures.
- Execution status.

**Important:** Never log passwords, access tokens, connection strings containing secrets, or sensitive personal data unnecessarily.

## 5. Metrics

### 5.1 What Are Metrics?

Metrics are numerical measurements collected over time to understand application and infrastructure performance.

Unlike logs, which describe individual events, metrics summarize behavior through numbers.

Example:

```text
Pipeline Duration: 45 minutes
Records Processed: 1,000,000
Failed Records: 250
CPU Utilization: 75%
Memory Utilization: 80%
```

Metrics help engineers identify trends, performance degradation, and unusual behavior.

### 5.2 Common Types of Metrics

| Metric | Meaning | Example |
|---|---|---|
| Counter | Cumulative count of events | Total failed records |
| Gauge | Value that can increase or decrease | Current memory usage |
| Histogram | Distribution of observed values | Request or task durations |
| Summary | Statistical summary of observations | Quantiles and count, depending on implementation |

These are common metric instrument types. Exact support and aggregation behavior depend on the monitoring system.

### 5.3 Counter

A counter generally increases over time and can be reset when the process restarts.

Example:

```text
Total Records Processed = 100000
Total Failed Records = 250
```

Useful for:
- Total successful records.
- Total failed records.
- Total API requests.
- Total pipeline executions.

For rates, calculate the increase in the counter over a time interval.

### 5.4 Gauge

A gauge represents a value that can increase or decrease.

Example:

```text
Current Memory Usage = 75%
Active Spark Executors = 8
```

Useful for:
- CPU utilization.
- Memory utilization.
- Active connections.
- Current queue size.

### 5.5 Histogram

A histogram records observations in buckets and typically provides a count and sum.

Example: Pipeline task duration.

```text
Task Duration:
0–10 seconds: 20 tasks
10–30 seconds: 50 tasks
30–60 seconds: 25 tasks
Above 60 seconds: 5 tasks
```

Useful for understanding the distribution of:
- API response times.
- Query execution times.
- Pipeline task durations.

### 5.6 Summary

A summary records observations and may calculate quantiles, depending on the implementation.

For example:

```text
Task Duration:
Count = 100
Average = 20 seconds
P50 = 15 seconds
P95 = 55 seconds
```

A summary and histogram are not interchangeable. Histograms can be aggregated across instances more flexibly when bucket boundaries are consistent.

### 5.7 Important Performance Metrics in Data Engineering

| Metric | Why It Matters |
|---|---|
| Pipeline duration | Identifies slow pipelines |
| Records processed | Measures workload volume |
| Records per second | Measures processing throughput |
| Failure rate | Identifies reliability problems |
| Data freshness | Measures how current the data is |
| CPU utilization | Identifies CPU pressure |
| Memory utilization | Identifies memory pressure |
| Shuffle read/write | Helps diagnose Spark performance |
| Executor failures | Indicates execution instability |
| Data quality failure count | Tracks invalid records |

### 5.8 Throughput

Throughput measures how much work is processed per unit of time.

Formula:

\[
\text{Throughput} =
\frac{\text{Records Processed}}{\text{Processing Time}}
\]

Example:

- Records processed = 600,000
- Processing time = 10 minutes

\[
\text{Throughput} =
\frac{600,000}{600}
= 1,000 \text{ records/second}
\]

### 5.9 Error Rate

Error rate measures the proportion of failed operations.

\[
\text{Error Rate} =
\frac{\text{Failed Operations}}{\text{Total Operations}}
\times 100
\]

Example:

- Total operations = 10,000
- Failed operations = 200

\[
\text{Error Rate} =
\frac{200}{10,000}\times100
= 2\%
\]

Define the denominator carefully. For example, distinguish failed records from failed pipeline runs.

## 6. Traces

### 6.1 What Are Traces?

Distributed tracing tracks the path of a request or operation as it moves across multiple services or components.

A trace helps engineers understand:
- Which components were involved.
- How long each operation took.
- Where delays occurred.
- Which service produced an error.
- How different operations are connected.

### 6.2 Example

Suppose an order-processing workflow uses several services:

```text
Order API
    |
    v
Customer Database
    |
    v
Kafka
    |
    v
Spark Processing
    |
    v
Delta Lake
    |
    v
Reporting Service
```

The complete execution can be represented as a trace.

Each individual operation is represented by a span.

### 6.3 Trace and Span

**Trace:** The complete journey of an operation through a distributed system.

**Span:** An individual unit of work within a trace.

Example:

```text
Trace: order_123

Span 1: Read order from API       100 ms
Span 2: Query customer database   250 ms
Span 3: Publish to Kafka           50 ms
Span 4: Process with Spark       2,000 ms
Span 5: Write to Delta Lake       500 ms
```

Total duration depends on the execution relationships. If spans run in parallel, their durations should not simply be added together.

### 6.4 Trace ID and Span ID

- **Trace ID:** Identifies the complete trace.
- **Span ID:** Identifies one individual operation.
- **Parent Span ID:** Identifies the parent operation when a span has a parent.

These identifiers help connect events across services.

Example:

```text
Trace ID: trace_abc123

Span 1:
  Span ID: span_001

Span 2:
  Span ID: span_002
  Parent Span ID: span_001

Span 3:
  Span ID: span_003
  Parent Span ID: span_001
```

### 6.5 Distributed Tracing

Distributed tracing is particularly useful when a workflow involves multiple applications, APIs, databases, and processing engines.

Without tracing, an engineer may need to inspect several independent logs to understand a single request.

With tracing, related operations can be connected using trace context.

### 6.6 OpenTelemetry

OpenTelemetry is an open-source, vendor-neutral framework for generating, collecting, and exporting telemetry data.

It supports:
- Logs.
- Metrics.
- Traces.

Important components:

| Component | Purpose |
|---|---|
| API | Interfaces used by application code |
| SDK | Implements telemetry creation and processing |
| Instrumentation | Captures telemetry from libraries and frameworks |
| Collector | Receives, processes, and exports telemetry |
| Exporter | Sends telemetry to a backend |

A typical architecture:

```text
Application
    |
    v
OpenTelemetry API / SDK
    |
    v
Instrumentation
    |
    v
OpenTelemetry Collector
    |
    v
Observability Backend
    |
    +---- Logs
    +---- Metrics
    +---- Traces
```

The Collector can receive, process, and export telemetry to supported backends.

## 7. Logs vs Metrics vs Traces

| Feature | Logs | Metrics | Traces |
|---|---|---|---|
| Data type | Event records | Numerical measurements | Execution spans |
| Main question | What happened? | How much or how often? | Where did time go? |
| Detail level | Often detailed | Usually aggregated | Operation-level |
| Best for | Error investigation | Trends and alerts | Distributed execution |
| Example | Database connection failed | CPU = 80% | Database span took 2 seconds |
| Typical storage | Log platform | Time-series database | Trace backend |

### Simple Way to Remember

- Logs explain events.
- Metrics show numerical behavior.
- Traces show execution flow.

## 8. How Logs, Metrics, and Traces Work Together

Consider a Databricks pipeline that normally completes in 20 minutes but suddenly takes 60 minutes.

### Step 1: Metrics Identify the Problem

The pipeline-duration metric shows that execution time increased from 20 to 60 minutes.

### Step 2: Traces Identify the Slow Component

Distributed traces show that the source database query is taking significantly longer than usual.

### Step 3: Logs Explain the Failure or Delay

Application and database logs reveal repeated connection timeouts.

### Step 4: Engineer Takes Action

The engineer investigates database availability, network connectivity, query performance, and retry behavior.

```text
             Pipeline Slows Down
                     |
                     v
                Check Metrics
                     |
                     v
            Identify Slow Component
                     |
                     v
                Check Traces
                     |
                     v
             Inspect Detailed Logs
                     |
                     v
              Identify Root Cause
                     |
                     v
               Fix the Problem
```

This is a common observability workflow.

## 9. Observability in Data Engineering Tools

### 9.1 Azure Monitor

Azure Monitor collects and analyzes monitoring data from Azure resources and applications.

It supports:
- Metrics.
- Logs.
- Alerts.
- Dashboards.
- Diagnostic settings.

### 9.2 Log Analytics Workspace

Log Analytics is used to store and query log data using Kusto Query Language (KQL).

Example:

```kusto
AzureDiagnostics
| where TimeGenerated > ago(1h)
| summarize EventCount = count()
    by Resource, OperationName
| order by EventCount desc
```

The actual table and column names depend on the resource and diagnostic configuration.

### 9.3 Databricks

Databricks provides execution and performance information through:
- Job run details.
- Task-level execution information.
- Driver and executor logs.
- Spark UI.
- System tables, where available.
- Integration with external monitoring platforms.

Important Spark metrics include:
- Input records.
- Shuffle read and write.
- Executor run time.
- Garbage collection time.
- Memory and disk spill.
- Failed tasks.
- Stage duration.

### 9.4 Apache Airflow

Airflow provides:
- Task execution logs.
- DAG run status.
- Task duration.
- Retry information.
- Scheduler and worker logs.
- Callback-based notifications.

Its UI helps engineers investigate task-level execution failures.

### 9.5 OpenTelemetry

OpenTelemetry can be used to instrument applications and services so that logs, metrics, and traces can be exported to compatible observability backends.

It is especially useful in systems where a data workflow crosses multiple services.

## 10. Correlation Between Logs, Metrics, and Traces

Correlation means connecting telemetry from different sources to investigate the same operation or incident.

Useful identifiers include:

- Pipeline ID.
- Pipeline run ID.
- Job ID.
- Task ID.
- Trace ID.
- Span ID.
- Request ID.
- Environment.

### Example

Suppose a pipeline fails during customer-data transformation.

The engineer can search using:

```text
Pipeline: customer_pipeline
Run ID: run_456
Task: transform_customers
Environment: PROD
```

If the application is instrumented for distributed tracing, the trace ID can connect related spans across services.

A consistent set of identifiers makes troubleshooting significantly easier.

**Important:** A pipeline run ID and a distributed trace ID are not automatically the same. They can be linked through custom attributes or correlation fields.

## 11. Data Engineering Observability Metrics

Traditional infrastructure metrics are not enough for data pipelines.

A data engineer should also monitor data-specific health.

### 11.1 Data Freshness

Measures how recently data was updated.

Example:

Expected update: 7:00 AM.

Actual latest update: 8:15 AM.

The data is 75 minutes behind the expected time.

### 11.2 Data Volume

Measures the number of records processed.

Example:

```text
Expected records: 100,000
Actual records:    12,000
Difference:       88,000
```

This may indicate an ingestion issue, source-system problem, or legitimate business change.

### 11.3 Data Quality

Tracks:
- NULL values.
- Duplicate records.
- Invalid values.
- Referential integrity failures.
- Schema violations.

### 11.4 Pipeline Reliability

Measures successful and failed pipeline executions.

\[
\text{Success Rate} =
\frac{\text{Successful Runs}}{\text{Total Runs}}
\times 100
\]

Example:

- Total runs = 100
- Successful runs = 98

Success rate = 98%.

### 11.5 Processing Latency

Measures the time taken for data to move through the pipeline.

For streaming systems, distinguish:
- Event time.
- Processing time.
- Ingestion time.
- End-to-end latency.

These represent different stages of data movement and processing.

## 12. Common Mistakes

1. Using logs as a replacement for metrics.
2. Collecting metrics without defining useful thresholds.
3. Logging sensitive information.
4. Creating too many high-cardinality metric labels.
5. Ignoring trace context propagation between services.
6. Treating a trace as a simple list of sequential operations.
7. Monitoring infrastructure but ignoring data freshness.
8. Storing logs without retention and access policies.
9. Using inconsistent pipeline and run identifiers.
10. Assuming that collecting telemetry automatically guarantees observability.

### What Is High Cardinality?

Cardinality refers to the number of unique values a metric label or dimension can have.

For example:

```text
Low cardinality:
environment = DEV, TEST, PROD

High cardinality:
customer_id = millions of unique IDs
```

Using highly unique values such as customer IDs, order IDs, or request IDs as metric labels can create a large number of time series and increase storage and query costs.

Use logs or trace attributes for high-cardinality details where appropriate.

## 13. Practical Interview Scenario

**Question: A Spark pipeline is taking three times longer than usual. How would you investigate the issue using logs, metrics, and traces?**

### Answer

I would investigate the issue in three stages.

**Step 1: Check Metrics**

Review:
- Pipeline duration.
- Input record count.
- CPU and memory utilization.
- Shuffle read and write.
- Executor failures.
- Data volume changes.

This helps identify when the performance degradation started and whether the workload or infrastructure changed.

**Step 2: Check Traces**

If distributed tracing is configured, inspect the execution path to identify which service or operation is taking longer.

For Spark-specific execution analysis, use the Spark UI to inspect jobs, stages, tasks, and shuffle activity. Spark UI is execution diagnostics, not itself distributed tracing.

**Step 3: Check Logs**

Inspect driver, executor, application, and source-system logs for:
- Connection timeouts.
- Out-of-memory errors.
- Repeated retries.
- Failed tasks.
- Data-skew symptoms.
- Source-system delays.

**Step 4: Identify Root Cause**

For example, a large increase in shuffle read and task duration may indicate data skew or an inefficient join.

**Step 5: Fix and Validate**

Optimize the transformation or resolve the infrastructure issue, rerun the pipeline, and compare the new metrics against the previous baseline.

## 14. Common Interview Questions and Answers

### Q1. What is observability?

Observability is the ability to understand a system's internal behavior using the telemetry data it generates.

### Q2. What are the three pillars of observability?

Logs, metrics, and traces.

### Q3. What are logs?

Logs are timestamped records of events generated by applications and systems.

### Q4. What are metrics?

Metrics are numerical measurements used to monitor performance, reliability, and system behavior over time.

### Q5. What are traces?

Traces track an operation as it moves across multiple services or components.

### Q6. What is the difference between a trace and a span?

A trace represents the complete operation. A span represents an individual unit of work within that trace.

### Q7. What is a Trace ID?

A Trace ID uniquely identifies a distributed trace and connects its related spans.

### Q8. What is structured logging?

Structured logging records events in a consistent machine-readable format, commonly JSON.

### Q9. What is OpenTelemetry?

OpenTelemetry is an open-source framework for generating, collecting, and exporting logs, metrics, and traces.

### Q10. What is the purpose of an OpenTelemetry Collector?

It receives telemetry, processes it, and exports it to compatible observability backends.

### Q11. What is the difference between a counter and a gauge?

A counter generally increases over time, while a gauge represents a value that can increase or decrease.

### Q12. What is a histogram?

A histogram records observations in configured buckets and provides information about their distribution.

### Q13. How are logs and metrics different?

Logs provide detailed event information, while metrics provide numerical measurements and trends.

### Q14. How do you monitor a Databricks pipeline?

Use job run details, Spark UI, driver and executor logs, performance metrics, and supported monitoring integrations.

### Q15. What is data freshness?

Data freshness measures how recently the data was updated relative to its expected delivery time.

### Q16. Why is correlation important?

Correlation connects related logs, metrics, traces, and pipeline executions so engineers can investigate an incident efficiently.

### Q17. What is high cardinality?

High cardinality means a metric has a large number of unique label or dimension values, which can increase monitoring-system resource usage.

### Q18. Is Spark UI the same as distributed tracing?

No. Spark UI provides Spark application execution diagnostics, while distributed tracing follows operations across instrumented services using traces and spans.
